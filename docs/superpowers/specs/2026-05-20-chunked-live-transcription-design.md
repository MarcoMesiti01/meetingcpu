# Chunked Live Transcription Design

## Goal

Improve meetingcpu for long meetings by replacing whole-recording transcription with a chunked local pipeline that saves in-progress transcript text during recording, supports live transcript updates, and adds optional local speaker labeling.

## Scope

This design covers:

- 30-second microphone chunks with a 5-second overlap.
- Server-side session jobs for chunk persistence, chunk transcription, live events, and final assembly.
- `transcript.in-progress.txt` saved locally after every accepted chunk transcript.
- Optional local speaker diarization using `pyannote.audio`.
- A quiet professional dashboard visual refresh.
- Existing upload transcription compatibility through the same chunk-oriented pipeline.

This design does not cover:

- Cloud transcription, cloud diarization, or cloud storage.
- Advanced biometric speaker identity across separate meetings.
- Perfect cross-chunk speaker matching in v1.
- Full-text retranscription of the complete meeting file at finalization.

## Product Behavior

### Live Meeting Flow

The browser creates a local session when recording starts. During recording, it captures 30-second audio chunks with a 5-second overlap and uploads each chunk to the Node server. The server saves every chunk under the session folder, transcribes each chunk independently with the local Python service, appends accepted text to `transcript.in-progress.txt`, and emits progress events to the browser.

When the user stops recording, the browser stops sending new chunks and asks the server to finalize the session. Finalization waits for queued chunks, assembles the final transcript from saved chunk results, writes `transcript.txt` and `transcript.json`, and marks the session complete. The final transcript is not generated by retranscribing the full recording.

### Local Files

Each session should use a structure like:

```text
data/sessions/<session-id>/
  chunks/
    chunk-000001.webm
    chunk-000002.webm
  recording.manifest.json
  transcript.in-progress.txt
  transcript.txt
  transcript.json
  metadata.json
```

The saved chunk set is the source of truth for the local recording in v1. `recording.manifest.json` lists chunk filenames, chunk indexes, chunk start/end times, overlap duration, MIME type, and byte sizes. The app will not create a combined `recording.webm` in v1 because naive WebM concatenation is unreliable; playback/export of a single combined recording can be added later with a media muxing step.

### In-Progress Transcript

The server appends chunk transcript text to `transcript.in-progress.txt` after a chunk is accepted and de-duplicated against overlap. This file must remain useful if the browser closes, the server stops, or a later chunk fails. It should include timestamps and speaker labels when available:

```text
[00:04:30] Speaker 1: Let's review the roadmap.
[00:04:36] Speaker 2: I think the main risk is installation.
```

If speaker labeling is unavailable, lines should omit the speaker or use a safe fallback such as `Speaker 1`.

## Architecture

### Browser

The browser owns microphone capture and chunk timing. It keeps the existing user-facing controls but changes the recording internals from one long `MediaRecorder` blob to chunk emission. The recorder emits 30-second chunk windows every 25 seconds, creating a 5-second overlap. To avoid invalid blob concatenation, overlapping windows are produced by short-lived `MediaRecorder` instances on the same microphone stream: recorder A captures seconds 0-30, recorder B captures seconds 25-55, recorder C captures seconds 50-80, and so on.

The browser uses:

- `POST /api/sessions` to create a session.
- `GET /api/sessions/:sessionId/events` to receive Server-Sent Events.
- `POST /api/sessions/:sessionId/chunks` to upload each chunk.
- `POST /api/sessions/:sessionId/finalize` to stop the session and write final transcript files.

The UI updates live as events arrive. It displays current status, queued/transcribed chunk counts, diarization availability, transcript text, errors, and the local path where in-progress transcript text is being saved.

### Node Server

The Node server owns session state and local persistence. It should add a session-oriented pipeline alongside the existing `/api/transcriptions` endpoint:

```text
POST /api/sessions
POST /api/sessions/:sessionId/chunks
GET /api/sessions/:sessionId/events
POST /api/sessions/:sessionId/finalize
```

Responsibilities:

- create session folders;
- save chunk files under `chunks/`;
- queue chunk transcription to avoid overloading CPU;
- call the Python service once per chunk;
- de-duplicate overlap text/segments before appending to in-progress files;
- persist chunk result JSON;
- emit session events over SSE;
- write final transcript files from saved chunk results;
- preserve partial transcript data on failures.

The current single upload endpoint should remain available. Uploaded files are saved locally, then split into 30-second chunk files with 5-second overlap before transcription. The implementation should use a local ffmpeg binary installed as a project dependency or discovered from `FFMPEG_PATH`; if ffmpeg is unavailable, the server returns a controlled error explaining that upload chunking requires ffmpeg. Microphone live chunking does not depend on ffmpeg.

### Python Service

The Python service continues to wrap faster-whisper locally. It should accept chunk audio and return a chunk result with:

- text;
- language;
- duration;
- segments with start/end offsets relative to the chunk;
- optional speaker labels per segment;
- diarization availability/status.

The service must not require cloud access at runtime. Whisper and diarization models must be downloaded during setup or through explicit local model download commands before offline use.

## Speaker Recognition

Speaker recognition will use optional local diarization through `pyannote.audio`.

Setup behavior:

- Whisper `small` remains the default model downloaded by `npm install`.
- Diarization is optional because pyannote models usually require accepting Hugging Face model terms and providing a token for first download.
- The app should expose a clear setup path for downloading diarization assets locally.
- If diarization assets or dependencies are missing, transcription still works.

Runtime behavior:

- If diarization is available, chunk segments receive labels such as `Speaker 1` and `Speaker 2`.
- If diarization is unavailable or fails for a chunk, the chunk transcript still completes without speaker labels or with `Speaker 1`.
- Speaker labels should be stable within each chunk.
- Cross-chunk label normalization should be best-effort in v1. The app should not claim biometric identity accuracy.

The UI should show whether speaker labels are available for the current session.

## UI Direction

The visual refresh should keep the existing functional controls but make the app feel like a quiet professional dashboard.

Design requirements:

- compact header with session state, model, diarization status, and elapsed recording time;
- clear title/model/start/stop/upload controls;
- transcript-first workspace for live chunk output;
- visible local save indicator for `transcript.in-progress.txt`;
- restrained colors, dense spacing, clean typography, and strong alignment;
- no marketing hero, no decorative gradients, no oversized cards;
- no change to core user workflow unless required for chunked live transcription.

The interface should make long-running meetings feel controlled: users can see that audio chunks are being saved, transcription is progressing, and partial text exists locally.

## Error Handling

Chunk failures should not erase prior progress. If one chunk fails:

- metadata records the chunk failure;
- the UI displays a recoverable warning;
- previously transcribed chunks remain in `transcript.in-progress.txt`;
- finalization can still produce a partial transcript with warnings.

If the Python service is unavailable, the server should keep saved chunks and metadata so the user can retry later. If diarization fails, transcription should continue without speaker labels.

## Testing

The implementation should include:

- session persistence tests for chunk naming, chunk result storage, in-progress transcript append, and final transcript assembly;
- server route tests for session creation, chunk upload, SSE event shape, finalization, and chunk failure metadata;
- Python tests for chunk transcription response shape, fake diarization success, and diarization fallback;
- frontend tests for chunk recording, event handling, live transcript rendering, diarization status, and finalize behavior;
- visual/CSS checks through build and browser smoke testing;
- full verification with `npm test`, `npm run build`, and a local dev smoke test.

## Acceptance Criteria

- A one-hour meeting does not require faster-whisper to process a one-hour audio file.
- During recording, transcript text appears chunk by chunk in the browser.
- During recording, `transcript.in-progress.txt` is updated locally after chunks complete.
- Stopping recording finalizes from saved chunk results without retranscribing the full recording.
- Speaker labels appear when local diarization is installed and configured.
- Transcription still works without diarization.
- The UI has a quiet professional dashboard style.
- Existing tests pass, and new tests cover chunking, live progress, failure recovery, and diarization fallback.
